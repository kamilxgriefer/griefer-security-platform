# Railway deployment images

| Service | Image built from | Public |
|---|---|---|
| `console` | `console/Dockerfile` | **yes** — the only public service |
| `api` | `Dockerfile` (repository root) | no |
| `opa` | `deployments/railway/opa/Dockerfile` | no |
| `nats` | `deployments/railway/nats/Dockerfile` | no |
| `postgres` | Railway's managed PostgreSQL | no |

## Why `api` and `console` are not duplicated here

Their production images already live at `Dockerfile` and `console/Dockerfile`,
and both already do what a platform needs: read `PORT`, bind every interface,
run as a non-root user, and carry no build toolchain.

Copying them into this directory would create two Dockerfiles per service that
must be kept identical by hand. They will not stay identical — one gets a
security fix and the other does not, and the divergence is invisible until the
wrong one is deployed. The platform is pointed at the canonical files instead.

`opa` and `nats` genuinely need their own images: the upstream ones ship no
policy bundle and no authentication, and both of those must come from this
repository rather than from a runtime mount.

## Build context

Both Dockerfiles here expect the **repository root** as their build context,
because they copy policy and configuration from it:

```bash
docker build -f deployments/railway/opa/Dockerfile  -t griefer-opa  .
docker build -f deployments/railway/nats/Dockerfile -t griefer-nats .
```

Set the corresponding service's root directory to `/` and its Dockerfile path
to the file above.

## Environment variables

Set these per service. Nothing here has a safe default: every value is
generated by `make secrets` and pasted into Railway's variable editor, never
committed.

### `console` — the only public service

| Variable | Value |
|---|---|
| `NODE_ENV` | `production` |
| `APP_ENV` | `production` |
| `RESPONSE_MODE` | `simulation` |
| `GRIEFER_API_BASE_URL` | `http://api.railway.internal:8080` |
| `INTERNAL_API_TOKEN` | must match the API's |
| `DEMO_SESSION_SECRET` | 48 random bytes, base64url |
| `GRIEFER_ADMIN_USERNAME` | `admin` |
| `GRIEFER_ADMIN_PASSWORD_SALT` | from `make secrets` |
| `GRIEFER_ADMIN_PASSWORD_HASH` | from `make secrets` |
| `GRIEFER_ANALYST_USERNAME` | `analyst` |
| `GRIEFER_ANALYST_PASSWORD_SALT` | from `make secrets` |
| `GRIEFER_ANALYST_PASSWORD_HASH` | from `make secrets` |

`GRIEFER_API_BASE_URL` uses Railway's private network name. It must **not** be
the API's public address, because the API should not have one — see below.

The administrator variables are required; the console refuses every request
without them rather than serving incident data behind an unconfigured gate. The
analyst variables are optional.

### `api` — private

| Variable | Value |
|---|---|
| `GRIEFER_ENV` | `production` |
| `GRIEFER_HTTP_ADDR` | `:8080` |
| `GRIEFER_ALLOW_PUBLIC_BIND` | `true` — binds `0.0.0.0` inside the private network |
| `GRIEFER_STORAGE_POSTGRES` | `true` |
| `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` |
| `GRIEFER_NATS_ENABLED` | `true` |
| `NATS_URL` | `nats://nats.railway.internal:4222` |
| `NATS_USER`, `NATS_PASSWORD` | must match the NATS service |
| `OPA_URL` | `http://opa.railway.internal:8181` |
| `GRIEFER_OPA_FAIL_CLOSED` | `true` |
| `RESPONSE_MODE` | `simulation` |
| `ALLOW_REAL_ACTIONS` | `false` |
| `SYNTHETIC_DATA_ONLY` | `true` |
| `SEED_SYNTHETIC_DEMO` | `true` for a populated demonstration |
| `INTERNAL_API_TOKEN` | must match the console's |

`GRIEFER_ALLOW_PUBLIC_BIND` is about the bind address, not exposure. The service
still has no public domain; Railway only routes to it from inside the project.

### `nats` — private

`NATS_USER` and `NATS_PASSWORD`, matching the API.

### `opa` — private

None. The policy bundle is baked into the image.

## Public exposure

Generate a domain for **`console` only**. `api`, `postgres`, `nats` and `opa`
must have no public domain at all — not an unlinked one, not one behind a
password. A private service with a public address is one misconfigured rule away
from being an open database.

After deploying, confirm it: every one of the four should fail to resolve.

## After the first deploy

1. Sign in as `admin` with the password from
   `~/.config/griefer/demo-credentials.txt`.
2. Check that `analyst` cannot reach `/audit` or `/admin/users`.
3. Record the console's URL in the credentials file, so whoever holds the
   password also knows where to use it.
